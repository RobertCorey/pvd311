# FixMyPVD: What Facade Apps Teach Us, and What To Fix

Synthesis of six research angles (fintech aggregators, civic-tech facades, browser-automation platforms, scraper-testing practice, sync patterns) plus a read of our own Worker. Everything below is grounded in the verified findings; recommendations that are our own design rather than borrowed are flagged **(our design)**.

## 1. What the best facade apps do differently

1. **Turn every failure into a typed state, never a generic "submit failed."** Plaid's Item error codes (`ITEM_LOGIN_REQUIRED`, `INVALID_MFA`, `ITEM_LOCKED`…) let a caller branch instead of retrying blindly. *For us:* a re-authable session must not hide behind a permanent validation reject — each class routes to a distinct handler (retry / re-login / scout / backoff / HITL / hard-stop), and a blind requeue after a real filing is exactly how we duplicate a city case.

2. **Keep two independent status fields, and treat the upstream's confirmation as the only receipt.** FixMyStreet runs its own state machine decoupled from the council's, defaults the council state to unknown, and won't call a report received until the backend confirms — a green DOM success screen is necessary but not sufficient. Open311 collapses rich statuses to open/closed with the verbatim string kept in a notes field. *For us:* a submit page backed by no case in My Requests is a silent-failure trap.

3. **Never mint a duplicate: idempotency key stamped into the upstream + check-before-create against the upstream's own list.** Stripe recognizes retries by a client key and replays the first result; Brandur pushes that key down into the foreign system so a later pass can match on it. *For us, the single most load-bearing lesson* — our portal drafts are permanent and undeletable, so a double-submit is unrecoverable garbage in the city queue. We already stamp `ref:<report.id>` into every case description and never read it back.

4. **Assume the join key arrives late or never; fuzzy-match and tolerate records that never reconcile.** Plaid links pending→posted via `pending_transaction_id` but designs for it being null (Capital One/USAA) or the pending item vanishing, and models the transition as remove-then-add so a bad match degrades to a visible orphan, not a corrupted row. Open311's token→ID (realtime/batch/blackbox) formalizes "no authoritative id at submit time." *For us:* the portal hands no case number synchronously, and permanent drafts may never become cases.

5. **Pull-based reconciliation on overlapping windows + a daily sweep; own all sync state; never infer a delete from an absent row.** FixMyStreet polls every ~15 min for the last 15 min plus an end-of-day full sweep, dedupes on a server-allocated id, and keeps the ledger entirely client-side. Nango warns incremental syncs can't detect deletions — a vanished row is not a deletion, a short page is not "everything's gone." *For us:* this is the direct answer to "sync is our biggest vulnerability."

6. **Deterministic-first, AI-on-drift, with a DOM fingerprint that doubles as a drift alarm — and verify the post-condition.** Stagehand caches a resolved selector and only re-calls the model when a DOM-hash fingerprint drifts; Skyvern caches per block so one changed step self-heals alone; the self-healing literature's failure mode is false positives (healing onto the wrong element), so you must confirm the intended outcome happened, not that a click dispatched. *For us:* cache the scout, and learn of drift from a monitor on Tuesday, not a resident on Thursday.

7. **You own neither the interface nor its uptime — keep your DB authoritative, gate tests behind a structural kill-switch, and guard the shared login as a crown-jewel SPOF.** Capital One cut Plaid off for a month in 2018 with no SLA; FixMyStreet's `STAGING_FLAGS`/`send_reports:0` make a forgotten env var fail *safe* (no real submission); Plaid vaults credentials in an HSM because a lockout is top-severity. *For us:* a Power Pages redesign or one account lockout stalls 100% of submissions at once.

8. **Own the whole citizen relationship, and don't overclaim.** Code for America's GetCalFresh decouples a clean intake from the bloated official form and owns the SMS/status loop the government won't. The FTC's $193K DoNotPay order punished the gap between a "robot lawyer" claim and untested output. *For us:* say "we file your report; the city triages," never "we fix it," and test that the city received a *correctly-categorized* case — a mechanically-green submit that landed mis-categorized is a quality failure the user can't see.

## 2. Our sync model today and where it breaks

| Failure mode | How we'd notice today | Consequence |
|---|---|---|
| Crash/timeout after `#NextButton` creates the case, before status write; reaper marks `failed`, retry re-files (no portal idempotency check; `ref:id` written but never read) | We wouldn't — nothing asks the portal "did I already file this?" | **Duplicate city case** in the permanent, undeletable queue |
| `extractCaseId()` reads newest grid row `nth(1)` positionally after navigating away, discarding the confirmation page/email | Silent; racing ticks can capture the previous case's id | Wrong id, or `submitted` with `portalCaseId=null` → watcher ignores it → **permanent orphan** |
| Engine lock is read-then-write (`getMeta`+`setMeta`, no CAS); `LOCK_MS`=12m < stuck window 20m | Not noticed | Two overlapping ticks both pass the guard → **double-submit** on the shared account |
| Submit-time dup gate queries only our DB `status='submitted'` within 24h/50m; never checks My Requests or city feed | Not noticed | A silently-filed (`failed`-recorded) report doesn't block its own duplicate; portal-direct duplicates invisible |
| Watcher joins on exact case-id; `if(!row) continue` — no absence path | Status silently freezes at last value | DB **drifts permanently** the moment a case leaves the grid |
| My Requests caps at `MAX_PAGES=20`, top-down; 0-row scrape → "skip diff" | Transient 0-row indistinguishable from "no change" | Oldest tracked cases fall past the horizon → **unwatchable**; a whole pass can no-op silently |
| Terminal-status regex `/resolved|cancel/i`; portal also uses `Closed`/`Completed` | No resolved-email copy; retention filter never selects the case | Photo never deleted → **30-day privacy promise broken**; case treated as open forever |
| `GetActivities` (per-case fulfillment feed) unused; status derived from grid only | Not noticed — grid shows intake, not fulfillment | Green status masks a city backend failure ("Update a Case Failed") → we report success on a dropped work order |
| Draft resume checks URL+selector, never verifies `entityId`; draft cleared only on `submitted` | Not noticed | Resume into wrong entity; dangling draft on a `failed` report is a loaded gun for the next retry |
| Proof key built as `…png` then stored as `${name}.png` → `.png.png`; save errors swallowed | Not noticed | Audit trail of what we filed is mis-pathed/absent exactly when a sync dispute needs it |

## 3. Recommendations, prioritized

### P0 — stop duplicating and orphaning city cases

- **Portal idempotency: check-before-create against My Requests.** Before `runWizard` files a new draft, scan My Requests for a recent case whose description contains `ref:<report.id>`; if found, bind that caseId and short-circuit. Files: `portal.ts` (extend `readMyRequests`/add a per-case detail read of `#description`), `engine.ts` (`submitOne` pre-submit read). **M.** Closes the reaper/retry double-submit hole. *(our design, per Stripe/Brandur/FixMyStreet)*
- **Split submit from case-id capture into two recovery points.** Read the id from the confirmation page/email at submit time (email subject already carries `PVD2026-…`), not the positional grid row. If capture fails, write `submitted_unconfirmed` (a new status the reconciler must resolve), never a clean `submitted` with a null key. Files: `portal.ts` (`extractCaseId`), `engine.ts` (`submitOne`), `contracts.ts`/`shared/types.ts`. **M.** *(our design, per Brandur recovery-points)*
- **Atomic engine lock.** Transactional compare-and-set / document precondition on `meta/engine`; raise `LOCK_MS` above the longest real submission. Files: `engine.ts` (`runTick`), `firestore.ts` (`patchDoc` precondition). **S.**
- **Recognize all terminal statuses.** Replace `/resolved|cancel/i` with the full set (`Resolved|Closed|Completed|Cancelled`). Files: `engine.ts`, `firestore.ts` (`findResolvedBefore`). **S.** Restores photo-retention and resolved emails — a privacy commitment.
- **Fix proof path + log failures.** Single `.png`, stop swallowing upload errors. Files: `engine.ts:168`, `portal.ts` (`saveProof`). **S.**

### P1 — resilience, reconciliation, drift, observability

- **Portal simulator + fixture harness (our design).** Because the integration surface is a JS-heavy Power Pages DOM, the highest-fidelity fake is not an HTTP mock but a tiny static site reproducing the DOM contract. Stand up a second Worker (or local Express) serving: `/SignIn` (real login selectors, sets auth cookie); `/my-requests/New-Request/` (exact `STEP1_SELECTORS` + honeypot + case-type launcher whose modal emits `.modal.in table tbody tr[data-id]` rows seeded from `scripts/case-type-census-2026-08-21.json`); a Step-3 partial per case type built from captured control snapshots; `POST /submit` echoing a fake `PVD2026-#####`; and `/my-requests/` returning the grid in `[role=grid] [role=row]` shape. Point `PORTAL_BASE_URL` at it and the whole live driver — login, wizard, `setControl`, scout, `parseRow` — runs end-to-end deterministically with zero city traffic. Add fault modes (rename a control id, add a required field, 500 the submit). Complement with Playwright `routeFromHAR` for the login/grid/lookup-modal paths (record with `--save-har-glob` covering `_services`/lookup calls; normalize out `__RequestVerificationToken`/`__VIEWSTATE` or POST-body matching breaks), and prefer committed rendered-DOM fixtures for Step-3. Files: new `worker/sim/`, `worker/test/fixtures/`, contracts around `PORTAL_BASE_URL`. **L.** *(per WireMock service-virtualization, Playwright mock, Plaid Sandbox caveat: fixtures decay, so pair with the canary below.)*
- **Reconciliation loop (our design).** A periodic `runReconcile` distinct from status polling: full-read My Requests, diff against our DB, and emit typed discrepancies — orphans (case in portal, no local `submitted`), our orphans (`submitted` with null caseId), stranded Drafts, missing case ids. The reaper must consult this before writing `failed` (reconcile-then-decide), binding `ref:id` matches instead of failing. Files: `engine.ts` (new pass + reaper hook), `firestore.ts`, `portal.ts`. **M.** *(per FixMyStreet overlapping-window + daily sweep, Merge/RPA reconcile.)*
- **Drift detection: control-schema contract + canary gate (our design).** Serialize `dumpControls()` per case type to committed golden JSON (id, label, kind, required, options); in `runDaily`, re-dump against the live portal and diff — a new required control, dropped option, renamed id, or vanished honeypot raises `PORTAL SCHEMA DRIFT` before the next submit trusts a stale mapping. Keep `canary()` non-mutating (never clicks Next/Submit) and gate the auto-submit engine on a fresh green canary. Files: `portal.ts` (`canary`/`dumpControls`), `engine.ts` (`runDaily`), fixtures. **M.** *(per Stagehand fingerprint, Context.dev structural diffing, Checkly synthetic monitoring.)*
- **Observability + sync-health panel on `/admin` (our design).** Persist per-step screenshot + trimmed DOM + network/console tail on every submit (Firebase Storage, expiring); surface a health panel showing canary status/last drift, orphan & stranded-draft counts, id-less-`submitted` count, and per-case-type submit success rate + scout invocation rate (a spike = drift early-warning). Files: `index.ts` (`/admin`), `health.ts`, `engine.ts`. **M.** *(per Browserbase observability, Plaid per-institution success metrics.)*
- **Watcher absence detection + targeted reads.** Add an "expected but not returned" path; target reads by tracked case-id rather than paging from the top; treat a 0-row grid as an error, not "no change." Files: `engine.ts` (`runWatcher`), `portal.ts`. **M.**

### P2 — UX honesty and hardening

- **Status honesty:** add `portalConfirmedAt` (set only when a caseId binds); gate the "filed as `<caseId>`" email and `/r/:id` on it, showing "Filing… / awaiting the city's confirmation" until then. `types.ts`, `engine.ts`, `me.ts`. **M.** *(DoNotPay/FTC + consistency-window.)*
- **Scout caching** keyed by case-type GUID + control-set fingerprint; re-call Claude only on fingerprint change. `scout.ts`, `firestore.ts`. **M.**
- **`GetActivities` per-case fulfillment polling** to catch dropped work orders behind a green grid. `portal.ts`, `engine.ts`. **L.**
- **Two dedup layers on create:** make the outbox always send a stable `clientId`; add a per-owner natural-key guard (owner+category+rounded-geo+window). `api.ts`, `engine.ts`. **S.**
- **Cancel/edit honesty:** state filed cases can't be retracted, or wire the city email-reply channel; track stranded public drafts. `me.ts`. **M.**

## 4. Testing plan

- **Unit (fixtures), local + CI, every commit.** Split fetch from parse; load committed saved-HTML per surface (My Requests grid, Step-1, Step-3 per high-volume case type) into a headless page from `file://`, and assert the pure logic that drifts: `parseRow` yields the right `PVD####-#####` + status column, `dumpControls()` yields expected control ids/options, `setControl()` fills each kind. No city contact. *(datawookie/Context.dev.)*
- **CI (simulator), every commit.** Point `PORTAL_BASE_URL` at the local Power-Pages-shaped mock; run the full driver end-to-end incl. a simulated submit; then run the **mutation/chaos suite** (rename a Step-1 selector, drop the honeypot, relabel grid columns, add an unseen required Step-3 control, return a dup-looking id) and assert the driver fails **loud** — `NEEDS_MAPPING`/`NEEDS_REVIEW` fires, schema-drift alarms, `parseRow` returns null — never a green submit. *(WireMock fault injection.)*
- **Nightly (zero-draft canary), real portal.** Non-mutating `canary()` (login → open wizard → open case-type modal → read grid, never Next/Submit) + schema diff vs golden JSON → drift alert; plus a low-cadence **inspect-mode** run against the real portal on a dedicated test account (stops before Submit, asserts the returned `controls`/`scouted` payload, not a screenshot). Run `runReconcile` here too. Creates zero city cases.
- **Release gate.** Block deploy unless unit + CI-simulator are green **and** the last nightly canary's schema matches golden (no unacknowledged drift). Auto-submit stays gated on a fresh green canary at runtime.

## Appendix — verified findings by angle (53 kept, 3 dropped)


### fintech (8 kept, 0 dropped)

- **Turn every headless-run failure into a typed, actionable state — never a generic 'submit failed'** (high) — Give the worker engine (engine.ts/contracts.ts) a typed error enum for the 3-step wizard and store the code on the case record: selector-not-found (drift), login/session expired, Step-3 unmapped control, portal 5xx/maintenance, validation rejection, account locked. Each maps to a distinct handler — retry, re-login, invoke the scout, backoff, HITL, or hard-stop — so the watcher knows which layer broke and a 'submit failed' never hides a re-authable session behind a permanent validation reject.  
  _evidence: https://codeswiftr.com/blog/plaid-engineering-deep-dive/ ; https://plaid.com/docs/errors/item/_
- **Track success rate per case-type / per wizard step so selector drift alarms before users notice** (high) — Instrument a success rate per case-type GUID and per wizard step, plus the scout LLM's invocation/failure rate — a sudden drop on one case type or a spike in scout usage is your selector-drift early-warning, since a portal change usually breaks one control, not the whole flow. Budget maintenance toward the few highest-volume case types rather than spreading it evenly; that's where the on-call load concentrates.  
  _evidence: https://codeswiftr.com/blog/plaid-engineering-deep-dive/ ; https://www.scale100.co/news/yodlee-bank-feeds-interview_
- **Model DB↔portal sync as a cursor-driven idempotent diff (added/modified/removed), commit the cursor only after a full persist** (high) — This is the direct answer to 'sync is the biggest vulnerability.' Don't re-scrape all of My Requests each poll and diff by hand; maintain a cursor/watermark, express each poll's delta as added/modified/removed keyed on the portal case number, apply the whole batch in one transaction, and persist the new watermark only after it lands. On any mid-poll inconsistency, replay from the old watermark — idempotency by stable key means replays are safe and no update is ever half-applied or silently dropped.  
  _evidence: https://plaid.com/docs/transactions/transactions-data/ ; https://plaid.com/docs/transactions/ ; https://plaid.com/docs/transactions/sync-migration/_
- **Assume the upstream key arrives late or never — build a fuzzy matcher and tolerate records that never reconcile** (high) — The portal doesn't hand you a stable case number at submit time — it appears later in My Requests, and permanent drafts may never become cases at all. Build a fuzzy matcher (submit timestamp + case-type GUID + address + description hash) to bind a locally-created report to the portal record when it surfaces, design explicitly for reports that never reconcile (the un-deletable draft that never advanced), and represent status changes as remove-then-add on a stable local id rather than in-place edits, so a wrong match degrades to a visible orphan instead of a corrupted case.  
  _evidence: https://plaid.com/docs/transactions/transactions-data/ ; https://www.mintactivate.com/bank-account-connection-issues-resolving-duplicate-transactions-in-mint_
- **When automation hits a wall it can't clear, emit an actionable human-in-the-loop step and resume from the minimum point** (high) — The hitl.ts instinct is correct and is the industry pattern. When the headless run meets MFA, a CAPTCHA, an unmapped Step-3 control the scout can't resolve, or an expired session, checkpoint the run state, emit a typed 'needs human' event, and resume from the minimum step — not a full wizard restart. Notify proactively before a session dies (mirror PENDING_EXPIRATION), and let some cases decline automation gracefully rather than looping on something a bot shouldn't solve.  
  _evidence: https://plaid.com/docs/link/update-mode/ ; https://developer.yodlee.com/resources/yodlee/multifactor-authentication/docs_
- **You control neither the interface nor its uptime — a redesign or block arrives with no notice and no SLA, so keep your own source of truth** (high) — A headless driver over 311.providenceri.gov is a dependency with no SLA: assume Power Pages redesigns, rate-limits, IP blocks, and CAPTCHA walls land unannounced. Keep your Firestore/DB as the authoritative record so a broken portal degrades to 'queued / pending re-submit' instead of data loss; add a canary (a periodic synthetic run or a DOM fingerprint of each wizard step) so you learn of drift from a monitor, not from a resident; and don't ship features that assume the portal keeps behaving.  
  _evidence: https://www.americanbanker.com/opinion/fintechs-vulnerability-apparent-in-capital-one-data-access-flap ; https://www.bankingdive.com/news/banks-to-tighten-third-party-data-access-in-2020-experts-say/5_
- **Scraping is a bridge, not a destination — the whole industry, far better resourced, fled to sanctioned channels the moment one existed** (high) — Treat the portal driver as an explicit, minimized stopgap. Invest now in any sanctioned durable channel — the public cityfeed you already poll, a records/FOIA contact, a real endpoint, or a direct relationship with the Providence 311 office — because organizations with vastly more engineering muscle concluded scraping doesn't scale as a foundation. Keep the driver behind the contracts.ts interface so it can be swapped for an official API without touching the rest of the app.  
  _evidence: https://fintechspecs.com/blog/plaid-vs-mx-vs-finicity/ ; https://codeswiftr.com/blog/plaid-engineering-deep-dive/ ; https://www.mx.com/guides/banking-apis-oauth-sceenscraping/ ; https://blog.logrocket_
- **The one shared session/credential is a crown-jewel single point of failure — vault it, throttle it, and alarm on lockout** (medium) — FixMyPVD drives the portal with a single project account, which centralizes both a security liability and a single ban/lockout that takes down 100% of submissions at once, not 1%. Vault the session/cookie and credential (encrypted at rest, rotated, isolated from the web tier), treat a lockout or 'action required' state as your highest-severity alarm, throttle and jitter submissions so the account doesn't look like a bot, and keep a documented re-auth runbook — because when that one login dies, every resident's report stalls simultaneously.  
  _evidence: https://codeswiftr.com/blog/plaid-engineering-deep-dive/ ; https://plaid.com/docs/errors/item/ ; https://www.fisglobal.com/insights/open-banking-and-the-departure-from-screen-scraping_

### civic (9 kept, 1 dropped)

- **Keep two separate state fields: our submission state vs the authority's mirrored state — "sent" is never "acknowledged"** (high) — Model at least two independent status fields on every case: (1) our pipeline state (queued / submitting / submitted / send-failed) and (2) the portal's mirrored state (unknown / acknowledged / in-progress / closed). Default the portal state to 'unknown', not to a copy of our submission state, and never render 'the city is working on it' just because the headless browser clicked submit. Map the Dynamics portal's rich statuses down onto a small canonical set and keep the city's verbatim status string in a notes field, exactly as GeoReport v2 does.  
  _evidence: https://fixmystreet.org/running/admin_manual/ ; https://fixmystreet.org/customising/integration/ ; https://wiki.open311.org/GeoReport_v2/_
- **Design for a deferred/absent case ID: the token→ID pattern (Open311 realtime vs batch vs blackbox)** (high) — The Dynamics portal is effectively a batch-or-blackbox service — with permanent, undeletable drafts, the real city case number often appears only later in 'My Requests'. Mint your own internal correlation/token ID at submit, mark the case_id as 'pending', give the user a receipt keyed on YOUR token immediately, and reconcile the real city case number asynchronously via polling. Critically, treat 'the real ID never arrives' (blackbox) as a first-class outcome, not an error — the user's receipt must not block on it.  
  _evidence: https://wiki.open311.org/GeoReport_v2/_
- **Reconcile by pulling on overlapping time windows plus a daily mop-up; own all sync state client-side** (high) — This is the blueprint for your DB↔portal sync (your stated biggest vulnerability). Poll GetActivities/My Requests on a short interval with deliberately OVERLAPPING windows (never assume the previous poll caught everything), dedupe by a stable update key so overlap and retries are idempotent, and run a periodic full sweep (daily) to catch anything the incremental polls missed. Never wait for the city to push you a notification — assume push never happens and make pull authoritative. Keep the 'last-seen / already-applied' cursor in your own store.  
  _evidence: https://www.mysociety.org/2013/02/20/open311-extended/ ; https://fixmystreet.org/customising/integration/_
- **Two-way ID mapping is the backbone of sync: store the authority's reference as external_id, stamp your own ID into the upstream** (high) — Capture and persist the city's case number as the join key the instant it appears in the portal, and — where a free-text field exists (description, reference, contact field) — stamp your own correlation ID INTO the Dynamics case at submit time. That gives you a way to re-find your case in 'My Requests' even when selectors, URLs, or list ordering drift, and it turns reconciliation from fuzzy matching (address+category+time) into an exact lookup. Fuzzy matching is your fallback, not your primary key.  
  _evidence: https://fixmystreet.org/customising/integration/ ; https://www.mysociety.org/2013/02/20/open311-extended/_
- **Build a structural staging kill-switch so tests cannot reach the real authority; make the unsafe path opt-in** (high) — Since your submit path necessarily touches the live city portal, add the equivalent hard rail below the business logic: a config gate whose DEFAULT in any non-production context is 'do not actually submit', with the real-submit path opt-in. Route test submissions to a project-owned test account, a dummy/sandbox category, or self, and make a forgotten env var FAIL SAFE (no submission) rather than fail open (a real case in the city queue). This is more robust than remembering to point tests at the right target.  
  _evidence: https://fixmystreet.org/customising/config/ ; https://fixmystreet.org/customising/send_reports/_
- **The upstream's confirmation, not the DOM success screen, is the authoritative receipt** (high) — Treat the headless browser's 'submission succeeded' DOM state as necessary-but-not-sufficient. Only advance a case to 'City has it' after you observe the portal's own confirmation — the case appearing in 'My Requests', a real case number, or a confirmation email. Until then, surface an explicit intermediate status like 'Submitted — awaiting city confirmation'. A green success page that isn't backed by a case in My Requests is a silent-failure trap.  
  _evidence: https://fixmystreet.org/running/admin_manual/ ; https://www.fixmystreet.com/about/open311-api-info_
- **A headless facade is a standing maintenance liability, not a one-time build — instrument for silent drift** (high) — Assume the city UI will change without notice and plan for it as an expected event, not an incident. Add synthetic health checks that submit/read on a schedule and alert on selector or page-shape drift BEFORE users hit it; keep your LLM 'scout' as the fallback for unmapped controls (you already have this) and log when it fires as an early-warning signal that a mapping went stale; and version your selector maps so a fast re-map is a config change, not a redeploy. Budget ongoing engineering for drift the way FMS budgets adapter maintenance.  
  _evidence: https://github.com/biglocalnews/civic-scraper/issues/91 ; https://groupbwt.com/blog/challenges-in-web-scraping/ ; https://www.mysociety.org/2013/09/09/councils-use-open311-and-youll-never-have-to-re-k_
- **Don't overclaim the automation, and test the actual submitted OUTPUT — the DoNotPay/FTC cautionary case** (high) — Be precise, in both UX copy and marketing, about what the facade guarantees: 'we file your 311 report on your behalf; the city triages and resolves it' — never 'we fix your problem' or anything implying official/city status.
