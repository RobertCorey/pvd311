# Engine ↔ portal sync — how we stay consistent (2026-08-23)

The city portal is the source of truth; our DB is a cache of intent + what we last saw. These are the rules that keep them from disagreeing (from `docs/research-facade-apps-2026-08.md` P0s, verified live 2026-08-23).

**Facts about the portal we rely on**
- A draft is created on Step 1 submit and is the case record itself (same GUID). Drafts are undeletable by constituents.
- The PVD number is assigned at draft creation. The running New-Request wizard does not show it; `my-requests/Edit-Request/?id=<GUID>` does (`input#title` = "PVD2026-87687 Pothole Report"). We read it from a side tab at draft-save time and again right before Submit → `portalDraft.caseId`, `portalCaseIdCandidate`.
- My Requests is a Fluent DetailsList with no GUIDs in the markup; rows are matched by PVD number only. Drafts appear there with status "Draft".

**Rules**
1. **Check-before-create.** If a report has `portalDraft.caseId`, look it up in My Requests first. Status ≠ Draft ⇒ an earlier attempt already filed it: record `submitted` with that number, log `submit.already_filed`, never run the wizard again.
2. **Case id is confirmed, never guessed.** After Submit we confirm the known number left Draft. No "first row" reads. If we can't confirm, the report is `submitted` with `caseIdPending: true` (admin shows it), detail "case number pending".
3. **Watcher reconciles pending ids** every 30 min by the candidate number: left Draft ⇒ confirm (`watcher.case_confirmed`); still Draft ⇒ the submit did not take ⇒ re-queue to resume the draft (`watcher.draft_not_submitted`).
4. **One tick at a time.** The engine lock is a compare-and-set on `meta/engine` (Firestore `currentDocument.updateTime` precondition); overlapping crons cannot both submit.
5. **Terminal statuses** are `Resolved|Closed|Completed|Cancelled|Canceled|Rejected|Withdrawn` (`TERMINAL_PORTAL_STATUS`): they drive the ops alert and photo retention (30 days after). Reporter status mail (any change) uses neutral words — Resolved reads "The city closed your request" — and is sent after the case-detail read so it can quote the city's Resolution Message verbatim. There is no public resolved count.
6. **Proofs** (viewport JPEG at submit / already-filed / inspect) live in Firestore `proofs/{reportId}_{name}`; failures are logged as `proof.failed` events; admin reads them at `GET /api/admin/reports/:id/proofs[/:name]`.
7. **Reconcile pass** (`runReconcile`, in `runWatcher` after the status diff; **flagged `RECONCILE_ENABLED`**, default off). A full My Requests scan → three typed discrepancies, keyed on the PVD number (rows expose no GUIDs; the write-only `ref:<report.id>` in each description is the guarantee a numbered row is ours, and every candidate report already carries that number as `portalCaseIdCandidate`/`portalDraft.caseId`, so we join on it):
   - **(a) Adopt.** A non-submitted report (`failed`/`rejected`/`auto-rejected`/`awaiting_review`, never the in-flight `pending`/`processing`) whose number shows as a **non-Draft** row ⇒ bind the number, set `submitted`, patch `portalStatus` from the row, record a `review` (`by: 'reconcile'`), log `reconcile.adopted`. Reporter-cancelled reports are never resurrected.
   - **(b) Stranded drafts.** A **Draft** row older than 24h whose report is `failed`/`rejected` ⇒ listed (drafts are undeletable — we cannot clean them), log `reconcile.stranded`. No status write.
   - **(c) Missing.** A `submitted` report with a `portalCaseId` no longer in the scan ⇒ flagged, log `reconcile.missing`. No status write. **Every scan is a window** (2026-10-30): live, My Requests shows only its newest 12 rows and `readMyRequestsPaged()` still reports `complete: true` (its pager selectors don't match the Fluent grid), so the 6 older of our 17 cases were flagged missing every run and the System sync light was red for 14 days. Now a case absent from the grid is flagged only when its PVD number is **after the oldest numbered row scanned** (the horizon; numbers follow the grid's Created On order, our own filing time doesn't match its local-time column), or when the detail read's grid search could not find it at any age (`portalSearchMissAt`, see 8). `complete` is advisory; on an incomplete scan the skipped older cases are logged once as `reconcile.partial_scan`.
   - Writes a snapshot to **`meta/reconcile`** `{ at, adopted: string[], stranded: string[], missing: string[], scanned, complete, error }` — all three arrays are **PVD case numbers** (per-report `reconcile.*` events carry the `reportId` for drill-down). `/api/admin/health`'s sync block (`adminapi.ts`) reads them shape-agnostically: it derives the displayed counts and the `ids: { adopted[], stranded[], missing[] }` (≤50 each) from these arrays. `complete` is false when the grid was truncated. `error` is `null` on a clean pass and carries the message when the pass throws (set from `runWatcher`, merged over the last-good counts, cleared on the next clean pass). **Never writes `failed`.** Idempotent across ticks: adopt leaves the candidate set once submitted; stranded/missing events fire only on first appearance (diffed against the prior `meta/reconcile`). A **0-row scan** is treated as a transient error (`reconcile.empty_scan`), never as "everything vanished"; a truncated grid no longer false-flags older cases as missing (self-heals via `reconcile.reappeared` if one does reappear).

**Step-3 control dump (schema 2, hidden included).** `collectStep3Controls` (portal.ts) dumps the WHOLE Step-3 conditional-control set — Step 3 renders ~43 inputs and toggles them per case type via `display:none`, so watching only the case type's one visible field misses drift in the shared set. Each dumped/normalized control now carries a **`visible: boolean`** (`offsetParent === null` ⇒ hidden). A radio group is `visible` if any member is shown. Only **visible** controls are filled/scouted at submit time (`fillStep3` skips hidden ones — a hidden control is not applicable to that case type); the full dump (visible + hidden) is what the canary snapshots and diffs.

**Diff (drift.ts).** Same-id controls are compared on label / required / options **and visibility** — a shown⇄hidden flip is drift (`visibilityChanged`), alongside the existing added / removed / renamed / required-changed / relabeled / options-changed. Id-set adds/removes and rename reconciliation (same label+kind) are unchanged; both dumps now include hidden controls, so a control fully disappearing is still `removed`, while one that merely hides is `visibilityChanged`.

8. **Case-detail snapshot (routing trail)** (`casedetail.ts`; `Portal.readCaseDetail`). The grid row opens a modal whose iframe holds the case form + a `.notes` timeline where the city's outbound dispatch emails appear ("PVD 311 → RI Energy", with internal `PVD311:nnnnnnn` ticket ids) — the only place routing is visible. The driver finds the row through the grid's own search box (one request, any age, no paging), dumps fields + notes (honeypot `frm_pref_*` never read; Submit / Add comment / Upload never clicked), closes the modal, clears the search. Stored raw on the report as `portalDetail` `{ capturedAt, hash, fields, notes[≤40, text ≤6k] }` plus derived `portalRouting[]` (`{ dept, at, ticket }`, oldest first) and `portalDetailCheckedAt`. **Cadence:** watcher = first sighting + any report whose grid status changed this run + ≤2 open cases past the grid's 12-row window (never-read-off-grid first, then least-recently-checked; ≤10/run in all); daily = open (non-terminal) cases least-recently-checked first (≤30/day). Bounded by the open set, never by lifetime volume. **Status past the window** (2026-10-30, `applyOffGridStatuses`): the read also returns the search row's Status Reason (`rowStatus` — the case status, never the work order's); for a case not in this run's grid rows the watcher patches `portalStatus`/history from it and logs `watcher.status` with `data.via: 'detail'`. A report's first such read (`portalOffGridAt` unset) is its backlog: caught up silently (no mail, no push). Later moves go through `notifyStatusChanges` like grid moves. `null` from the read means only "searched, no such case" (sets `portalSearchMissAt`, cleared by the next read that finds it); a grid or modal that never rendered throws. **Events:** `watcher.detail_captured` (first), `watcher.detail_changed` (`warn` when a note from the city arrived, `info` for our own; `data.newNotes` previews, `changedFields`, `routing`, `newDepts`), `watcher.detail_unavailable` (search found no such case), `watcher.detail_failed`. Equal hash ⇒ only `portalDetailCheckedAt` moves. Nothing is shown in the app yet — by design we keep everything because we don't yet know which parts matter; /admin's raw JSON has it.

**Golden schema versioning.** Goldens (`GoldenSnapshot`, `meta/golden_<category>`, and the committed sim goldens under `worker/test/golden/`) carry a **`schema`** (`GOLDEN_SCHEMA = 2`; absent ⇒ pre-versioning = 1). A schema-1 golden captured a different shape (visible-only, no `visible` flag), so it is **not comparable** to a schema-2 dump. `recordControls` **re-mints** (emits `canary.golden_minted`, no drift, no alert) when the effective baseline is the sim fallback, absent, **or a live golden at an older schema** — instead of diffing across schemas. This is how the production schema-1 live goldens migrate on their first post-deploy live dump with no false `+N added` storm; from the next dump on it's live-vs-live at schema 2. `writeLiveGolden`/`rebaselineGolden` stamp the current schema.

**Sim goldens.** Regenerated from the simulator (`cd worker && GEN_GOLDENS=1 npx vitest run test/golden/generate.test.ts`) through the real `collectStep3Controls` in a real Chromium; the sim's Step 3 renders one shared hidden control (`cop_priorcaseref`, `display:none`, unmapped) so each golden includes a `visible:false` entry, mirroring the live shared set in miniature. `worker/src/golden-controls.ts` is the regenerated runtime barrel.
