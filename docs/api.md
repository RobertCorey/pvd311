# FixMyPVD Worker API — v1 (wire truth)

Base: `https://pvd311-worker.pvd311-worker.workers.dev` (custom domain at launch). CORS: pvdsnow.org, www, the two Firebase Hosting domains, `http://localhost:*`.
Errors: `{ "error": "<code>", "field"?: "<name>", "retryAfterSec"?: n }` with 400/403/404/429/500. The client never blocks on intake errors.

## POST /api/report — create a report
**Requires an account**: `Authorization: Bearer <Firebase ID token>` (see Accounts) → 401 `auth_required` without one. The report's `ownerUid` and `reporterEmail` come from the token (email only when the account's `prefs.emailUpdates` is on). Reporter quota (docs/quota.md, worker/src/quota.ts): per mailbox 5/day + 15/week, 60 s between reports; per IP 30/day. Days reset 00:00 America/New_York, weeks Monday 00:00 ET. Every accepted report counts; a reporter cancel before filing refunds its day + week.
`multipart/form-data`:
| field | rules |
|---|---|
| `category` | key from `shared/categories.ts` |
| `description` | ≤ 2000 chars (optional) |
| `address` | 3–500 chars |
| `lat`, `lng` | both or neither; inside Providence bbox (41.70–41.92, −71.52–−71.33) |
| `extra` | JSON object string, ≤ 8 keys (per-category answers, e.g. `{"size":"Medium (~28in)"}`) |
| `name` | optional |
| `deviceId` | random uuid persisted on the device (recorded for abuse forensics; pacing is per account + IP) |
| `appVersion` | string |
| `clientId` | uuid generated once per report attempt and reused on outbox retries → idempotent: a repeat returns the existing `{id,…}` with 200 and `idempotent:true` |
| `descriptionOriginal`, `intakeFlags` | from intake, optional |
| `photo` | image/*, ≤ 5 MB; required unless the category has `photoRequired:false`. Client should compress to ≤ ~300 KB. |

201 → `{ id, trackingUrl: "/r/{id}", category, createdAt }`. `id` is the tracking token (22 chars, unguessable).
Errors: `auth_required` (401), `invalid_category`, `invalid_address`, `too_long`, `lat_lng_pair`, `invalid_coords`, `outside_providence`, `invalid_extra`, `photo_required`, `invalid_photo`, `rate_limited` (429: `{ error, reason: 'gap'|'day'|'week'|'ip', retryAfterSec, quota }`, `quota` as in `GET /api/me`).

## POST /api/intake — moderation + optional wording cleanup (AI)
JSON `{ category|null, description, address, extra?, hasPhoto, appVersion }` →
`{ polishedDescription: string|null, flags: ('spam'|'abuse'|'personal_info'|'not_311'|'emergency')[], note: string|null, model: string|null }`.
Rate-limited 10/min per IP and 1,500/day globally (durable, Firestore meta). The flags are advisory for the client; the Worker re-runs moderation itself before any auto-approval (see HITL). Never suggests a category (the reporter picks). Client shows: `emergency` → 911 notice; `not_311` → notice; others are passed back as `intakeFlags` and force human review server-side.

## GET /api/reports/:id — tracking (no PII)
`{ id, category, categoryLabel, address, lat, lng, photoUrl|null, createdAt, status, portalCaseId|null, portalStatus|null, resolutionMessage|null, timeline: [{at, label, kind?, text?, vars?}], workOrder|null, department|null, cityAsk|null, nextUpdateHint|null, hasEmail, owned, cancelledByReporter, notFiled: { code: 'cancelled'|'reviewed'|'duplicate'|'outside'|'no_photo'|'no_address'|'blocked'|'other'|'failed', text, duplicateOf } | null }`
`notFiled` is set whenever the report will not / did not reach the city: reporter-safe text (admin-entered reason when there is one; never the reviewer's identity), and `duplicateOf` = the other report's id for the duplicate case (link "View that report").
`status`: `received` | `sending` | `sent` | `needs_attention` | `rejected`. `portalStatus` (from the city): `Submitted` | `Assigned` | `In Progress` | `Department Responded` | `Resolved` | `Cancelled` | `Merged` (others pass through verbatim).
Client label map: received → "Received"; sending → "Sending to the city"; sent → "Sent" + case id; needs_attention → "Needs attention — we're looking at it"; rejected → "Not filed".

`resolutionMessage`: the city's own "Resolution Message" (portal field `adx_resolution`, from the watcher's case-detail snapshot), verbatim (trimmed), public, any status; null when empty. Never parsed — the city's "Resolved" can mean "referred elsewhere" (PVD2026-90091). The app shows it as "The city's note:" and says "The city closed this request" in its own words.
Timeline rows: `label` is always an English fallback; rows with a `kind` are worded by the app. Relayed city email by what it is (`worker/src/cityask.ts` classifies at arrival; older rows by the same rules on read): `city_receipt` (the city's receipt — shown once), `city_routed` (`vars.dept` = its "Department Assigned:", verbatim), `city_message` (anything else; `label` carries the subject). `city_ask` = the city asked for more information (one row per ask, whichever channel it came on), `city_answer` = an answer went to the city (sent ones only), `work_order` = the city's work order changed (`vars.number`, `vars.status` verbatim; `at` = the city's completion time when it says Completed, else when the watcher saw it). `text` (the city's plain-text words minus `[cid:…]` lines — or, on `city_answer`, the reporter's answer) is added only for the report's owner and only on this single-report read — never public (city emails can quote the reporter's description and address) and never in `/api/me/*` lists.

`workOrder`: `{ number|null, status, completedAt|null }` from the portal case detail (`cop_workordernumber` / `cop_workorderstatus` / `cop_workcompletedon`), verbatim; null when the case has none. Its status is the work order's, not the case's — PVD2026-90090 showed "Department Responded" with its work order "Completed" (stamped before the case was routed, so possibly a linked existing job). The app says "The city marked its work order complete; the case itself is still open", never "fixed".
`department`: the "Department Assigned:" of the city's routing email (else the portal timeline's last dispatch), verbatim; null when unknown.
`cityAsk`: the newest time the city asked the reporter for more information, or null. Public: `{ askedAt, open, answered, answeredAt }` — `open` = still answerable and not answered yet. The owner also gets `{ id, canAnswer, expiresAt }`, and on this single-report read `{ text, answers: [{ at, via: 'app'|'email', status: 'sent'|'blocked'|'failed', text }] }`. Answerable while the report is `sent`, the city case is not terminal, fewer than 3 answers were sent, and for 14 days.

## POST /api/reports/:id/answer — the owner answers the city (account required)
JSON `{ text, askId? }` (`askId` defaults to the newest ask) → `{ ok: true, answer: { at, via: 'app', status: 'sent', text } }`. The Worker runs moderation (blocks `spam` / `abuse` only) and mails the answer to the city FROM the portal account's contact address (`RELAY_ADDRESS`, cases@fixmypvd.org) to the city address that asked, subject `RE: <the city's subject>` (keeps the city CRM's `PVD311:nnnnnnn` token so it threads onto the case) + the case number, with the original address / map link / description for context. Every attempt is recorded on the report (`cityAsks[].answers`). Errors: `unauthenticated` (401), `not_owner` (403), `not_found` (404), `invalid_text` (400: empty or > 2,000 chars), `no_ask` / `case_closed` / `expired` / `too_many` (409), `too_soon` (429, `retryAfterSec`; 60 s between answers), `blocked` (422, `flags`), `send_failed` (502; you are alerted, the owner may retry). The same answer can come by email: the owner replying to our "The city needs more information" mail (relay.ts; sender = the owner's address with DMARC pass, the top of the reply above the quoted message).

## GET /api/nearby?lat=&lng=&category=&radiusM=75
`{ items: [{ id, source: 'snappvd'|'city', category, categoryLabel, lat, lng, address, createdAt, status, portalStatus, distanceM }] }` — reports within `radiusM` metres (default 75, max 2000) of `lat,lng`, from the last 14 days, both sources, sorted nearest-first. `category` (a `shared/categories.ts` key) optionally filters. ## GET /api/street?lat=&lng=&radiusM=300&days=30 — "My street" (added 2026-10-25)
`{ items: [{ id, caseType, category, street, status, open, createdAt, closedAt, resolution, lat, lng, distanceM }], radiusM, days, at }` — everyone's cases from the city's public list (`cityCases`, worker/src/street.ts) within `radiusM` metres (50–1000) of `lat,lng` that were created or closed in the last `days` (1–90), newest activity first. `resolution` is the city's own Resolution Message (closed cases only). Public; cached 5 min. Coordinates come from a one-time ArcGIS geocode of the case's street (cases without one are left out). Errors: `invalid_coords` (400, also for points outside Rhode Island). The app page is `/street?lat&lng&q=<address>`. The /street page now reads /api/street/map; this endpoint remains for the weekly digest and old links.

## GET /api/street/map?days=30 — the /street map feed (added 2026-10-25)
The map-first `/street` page's ONE request: every non-draft case from the city's public list (`cityCases`) created or closed inside the window — located and unlocated — as columnar tuples plus two index tables, so pan/zoom/filter/cluster/counts all happen in the browser from one array (`app/src/lib/streetMap.ts`) and never touch the network again. Public, no auth, same CORS as the other GETs; routed before `/api/street` in worker/src/api.ts. Pure builder `mapFeed(rows, { days, now, truncated })`, handler `handleStreetMap(url, store)` in worker/src/street.ts; types `MapFeed` / `MapItem` exported there and mirrored in `app/src/api/street.ts`.

**`days`** is snapped so the HTTP cache and the per-isolate cache hit (`snapDays`): missing / NaN / ≤ 0 → 30; 1–7 → 7; 8–30 → 30; > 30 → 90 (MAX_DAYS). The app only asks for 30 and 90 ("This week" is cut client-side from the 30-day set).

**Response** `200 application/json`, `cache-control: public, max-age=300` (no ETag in v1 — `at` changes per isolate load; the client's 5-minute module cache plus the HTTP cache cover revisits). Reads share the existing 5-minute per-isolate `loadCases` cache with `/api/street` and `/api/street/city` (one Firestore read per window per 5 minutes, loaded over `days + 60` so a case closed this month but opened in August still shows).
```json
{
  "v": 1,
  "days": 30,
  "at": "2026-10-25T17:00:00.000Z",
  "total": 1234,
  "located": 1108,
  "truncated": false,
  "types": [["Pothole", "pothole"], ["Missed Trash Day Pick-up Issue", "missed_trash"], ["Street Light Out", "street_light"]],
  "statuses": ["Submitted", "Assigned", "In Progress", "Department Responded", "Resolved", "Closed", "Cancelled", "Merged"],
  "items": [
    ["5f0efb0b-0454-ef11-a317-001dd8068673", 0, 1, 29876650, 0, 41.82834, -71.40061, "10 Angell St", 0],
    ["1ee8b671-7a2e-ef11-840a-001dd8039400", 2, 4, 29870210, 29876100, null, null, "", "Bulb replaced."]
  ]
}
```
- `at` — when this response was built. `total` — non-draft cases created or closed inside the window (unlocated included). `located` — of those, with coordinates. `truncated` — true when the load hit LOAD_LIMIT (3000 rows over `days + 60`), so the 90-day window may be missing its oldest cases.
- `types` — index = `t`; `[city caseType, category key]`, one entry per caseType (first-seen category wins, `'unsure'` when the doc has none); ~40 entries. `statuses` — index = `s`; starts with the eight known statuses in that order, any other status string seen is appended.
- `items` — one tuple per case, columns `[id, t, s, createdMin, closedMin, lat, lng, street, res]`: `id` the city's GUID; `t` / `s` indexes into the tables; `createdMin` = floor(createdAt / 60 s) in UTC minutes, 0 when unparseable; `closedMin` = floor(closedAt / 60 s) for closed cases (the city's resolutionDate, else the statusSeen close we watched — `cityinsights.closedAt`), 0 when open/unknown; `lat` / `lng` rounded to 5 dp or `null` when the case has no coordinates; `street` `""` when blank; `res` the city's Resolution Message trimmed and cut to 300 chars, or `0` when absent (read `res || null`).
- Inclusion and order are exactly `/api/street`'s: `status` matching `/^draft$/i` is skipped, a case is kept when `max(created, closed) ≥ now − days`, sorted newest activity first (array order is the tiebreak). `open` is not transmitted — derive it as `!CLOSED.has(statuses[s])` with CLOSED = Resolved, Closed, Cancelled, Merged.
- Size (measured shape): ≈ 131 B per item raw → 30 days ≈ 1,200 items ≈ 157 KB raw + 3 KB tables ≈ 50 KB on the wire with Cloudflare brotli (the GUIDs are the ~26 KB floor); 90 days ≈ 3,000 items ≈ 390 KB raw / ≈ 120 KB wire, fetched only when "90 days" is chosen.

## GET /api/street/case/:guid — one case for a deep link (added 2026-10-25)
`/street?case=<guid>` (the follow mail's "See it on the map", a `/my` row) must open the card even when the case is older than the page's loaded window (30 or 90 days) — following is for long-lived cases. When the page does not find `case=` in its feed it asks for the case itself; `guid` = the city's case GUID, `/^[0-9a-f-]{36}$/` (400 `invalid_id` otherwise). → `{ id, caseType, category, street, status, open, createdAt, closedAt, resolution, lat, lng, updatedAt, detail? }` — the `GET /api/me/city` item without `followedAt`, plus `detail` below (worker/src/street.ts `handleStreetCase`, `StreetCaseView`). 404 `not_found` when there is no record or it is a draft (the feed skips drafts too); only then does the page say the request is gone. Public, no auth; one Firestore doc read; `cache-control: public, max-age=300` (60 on a 404). Routed before `/api/street` in worker/src/api.ts.

**`detail`** (added 2026-10-27, for the pin overlay — "when you click on a pin it should show an overlay with all the case details") — optional; **omitted** until the sync has read the case's detail form (no `cityCases/{guid}.detail` yet). Built by `streetCaseDetail(doc)`; values are plain strings (the app escapes).
```json
"detail": {
  "address": "10 Example St, Providence, RI, 02908, USA",
  "timeline": { "reported": "2026-10-16T12:58:01.000Z", "received": "2026-10-16T12:58:18.000Z", "routed": "2026-10-16T12:58:33.000Z", "workCompleted": null, "resolved": "2026-10-22T14:45:00.000Z" },
  "answers": [{ "label": "Type of Property", "value": "Residential (someone else's property)" }, { "label": "Is Property Abandoned", "value": "Yes" }],
  "statusHistory": [{ "status": "Submitted", "at": "2026-10-16T13:00:00.000Z" }, { "status": "Assigned", "at": "2026-10-17T10:00:00.000Z" }, { "status": "Resolved", "at": "2026-10-22T15:00:00.000Z" }]
}
```
- `address` — the city's full address from the form (`detail.address`), trimmed; null when blank.
- `timeline` — ISO or null each: `reported` = the case's `createdAt`; `received` / `routed` / `workCompleted` = the form's `receivedOn` / `routedOn` / `workCompletedOn`; `resolved` = the form's `resolutionDate`, else — for a case closed now — the close we watched (`cityinsights.closedAt`, the same value as `closedAt`).
- `answers` — the city-question answers (`detail.answers`) that have a form label (`detail.labels[id]`; unlabelled ones are skipped), in the order the stored record lists them (the city form's own layout order is not stored — the seed's per-type lists are alphabetical too), each `{ label, value }` with a checked "Yes" radio as `"Yes"` and blanks dropped. **An allowlist** (`publicAnswer` in street.ts, unit-tested; Rob 2026-10-27: keep plates and names hidden): only a city dropdown's choice, a "Yes" radio, or one of the hand-read typed boxes in `PUBLIC_TEXT_FIELDS` (pole number, number missed, needed parts) — never any other typed box or lookup, where plates and names end up whatever the box is called. The answer's kind is `detail.kinds[id]` (stored since DETAIL_VERSION 3; an older read shows only its "Yes" radios and the hand-read boxes until the sync re-reads it, new and changed cases first). On top of that, `isPrivateCityField(id, label)` drops any answer whose label or field id looks like a licence/license plate, tag or registration number, a VIN, the abandoned-vehicle "Vehicle Details" box, or names or reaches a person — owner, landlord, tenant, complainant, contact, name, phone, email — whatever its kind. The stored record is unchanged — citycases.ts still keeps the whole public form; this decides only what the endpoint republishes.
- `statusHistory` — `cityCases.statusSeen` (status key → when the sync saw the case enter that status; a status entered twice keeps the later time) as `{ status, at }`, **oldest first**; the key is mapped back to the city's status string (`In_Progress` → `In Progress`); Draft and unparseable times are dropped. `[]` when nothing was seen.

## GET /api/week — "This week in Providence" (added 2026-10-25; `?until=` 2026-10-26)
7 days of the city's public 311 list, citywide, against the 7 before — the `/week` page's one request and the body of the Monday `week_digest` mail (worker/src/week.ts: pure `weekSummary(rows, { now, hoodOf, until })`, window `resolveWindow(until, now)`, handler `handleWeek`). Public, no auth; `cache-control: public, max-age=300`; one summary per week is built at most once per 5 minutes per isolate (keyed `'now|<today>'` for the current week — so it is not served as current past New York midnight — else `untilDate`) from street.ts's `loadCases` (one Firestore read per load window, + the 60-day close lookback).

**`until=YYYY-MM-DD`** (optional) — a stable, shareable week: the 7 **New York calendar days** ending at the END of that date (`since` = 00:00 of `until − 6`, `until` = 23:59:59.999 of that date; 167 or 169 h across a DST change), `prev` = the 7 calendar days before. **Omitted, empty, or today's NY date → the current week**, i.e. today's behaviour (`since = now − 7 d`, ending now) — so the dated link of today's page (`/week?until=<today>`) is the same page today and becomes the full-day week at midnight. Archive floor: **56 days** back from today (NY). Errors: `invalid_until` (400 — malformed, not a real date, or after today in New York), `too_old` (400 — before the floor). Loading: the current week reads `loadCases(store, 14)` (rows 3000 = `LOAD_LIMIT`); **every** dated week reads the same `MAX_LOAD_DAYS` = 70-day window (+ the 60-day lookback) with `ARCHIVE_LOAD_LIMIT` = 6000 rows, so the eight archive weeks share one `loadCases` entry and one Firestore read per 5 minutes instead of a distinct 6000-row read each (130 days of the city's 30–47 cases a day overflow 3000, and the query is newest-first, so the oldest — wanted — rows would be the ones cut; `weekSummary` filters the surplus).
```json
{
  "days": 7, "since": "2026-10-18T12:00:00.000Z", "until": "2026-10-25T12:00:00.000Z", "at": "2026-10-25T12:00:00.000Z",
  "untilDate": "2026-10-25", "prevUntil": "2026-10-18", "nextUntil": null, "current": true,
  "total": 312, "open": 172, "closed": 140, "located": 280,
  "prev": { "total": 298, "closed": 146 },
  "topTypes": [{ "caseType": "Pothole", "category": "pothole", "n": 48, "prevN": 40 }],
  "neighborhoods": [{ "name": "West End", "slug": "west-end", "n": 31, "open": 19, "closed": 12, "medianCloseDays": 2.5 }],
  "outcomes": { "work_done": 61, "enforcement": 4, "referred": 12, "logged_elsewhere": 9, "info_only": 6, "no_action": 40, "cancelled": 8 },
  "medianCloseDays": 3.5,
  "notable": [{ "id": "<guid>", "caseType": "Pothole", "category": "pothole", "street": "10 Angell St", "neighborhood": "College Hill", "status": "Resolved", "closedAt": "2026-10-24T14:02:00.000Z", "resolution": "Filled.", "lat": 41.82834, "lng": -71.40061 }],
  "busiestDay": { "date": "2026-10-21", "n": 64 }
}
```
- `untilDate` — the New York calendar date the window ends on: the `?until=` that names this week (`/week?until=<untilDate>` is what the page's Share copies and what the Monday mail links). `prevUntil` — `untilDate − 7 d`, null when that week is below the 56-day floor. `nextUntil` — `untilDate + 7 d`, null when that would be after today (NY). `current` — true when the window ends now (no `until`, or `until` = today).
- **Inclusion** is `/api/street`'s (cityOverview / nearbyCases): `status` matching `/^draft$/i` is skipped; a case counts for a week when its `createdAt` **or** its closedAt (the city's resolutionDate, else the statusSeen close we watched — `cityinsights.closedAt`) falls inside that window; it counts as **closed** there when its status is closed now and that close is not after the window's end (an undated close goes by its creation) — so for a dated week a case opened inside it and closed the week after is one of that week's *open* requests, as it was then. **This week** (current) = `[since, now)` with `since = now − 7 d` (equivalent to `max(created, closed) ≥ since`, so `total` equals the `/street` landing's "This week" count); **last week** (`prev`) = the 7 days before `since` by the same rule, so `prev` is what this endpoint reported a week earlier and the delta is like for like. A case created ten days ago and closed two days ago is therefore in both: in `prev.total` (and its type's `prevN`) as a new request, in `total`/`closed` as a close. `prev.closed` counts closes dated last week plus closed cases without a known close time that were created last week. For the current week `until` = `at` = when the summary was built; for a dated week `until` is 23:59:59.999 NY of `untilDate` (inclusive) and `at` is still the build time.
- `open` / `closed` — of this week's cases, by status outside / inside Resolved, Closed, Cancelled, Merged. `located` — with coordinates.
- `topTypes` — the six case types with the most cases this week (ties: name asc), each with last week's count `prevN` (0 when none). `category` = the doc's picker key, `'unsure'` when it has none.
- `neighborhoods` — every one of the 25 official neighborhoods with activity this week, n desc (name asc on ties); `open` / `closed` by the same window rule as the top-level counts (a dated week's case closed the week after is `open` here too, so Σ `closed` ≤ `closed`); located cases only, by point-in-polygon over `shared/neighborhoods.ts` (`hoodOf`); a point outside every ring (the bay, Pawtucket) joins none. `slug` = `hoodSlug(name)`, the `/street?n=` value. `medianCloseDays` (added 2026-10-27) — the hood's own median days created → closed over this week's closes in it with both times known, by the same rule and 1-dp rounding as the top-level `medianCloseDays` (week.ts `medianDays`); null when the hood had no such close. The app reads it as optional (an older Worker omits it). `/week` shows it as each row's "N closed · median X days" line and, for a signed-in reader's saved places, the "In <hood>, closed requests took a median X days — the city's was Y." line.
- `outcomes` — this week's **closed** cases by what closing meant, from `cityinsights.outcomeOf` (Cancelled / Merged → `cancelled`; otherwise `classifyResolution` over the Resolution Message: `work_done` · `enforcement` · `referred` · `logged_elsewhere` · `info_only` · `no_action`, the last also for a blank note). The seven always sum to `closed`.
- `medianCloseDays` — median of (closedAt − createdAt) in days over this week's closes with both times known, 1 dp; null when none.
- `notable` — this week's closes that carry a Resolution Message, newest close first, ≤ 12; `resolution` trimmed and cut to 240 chars; `neighborhood` / `lat` / `lng` null when unlocated; `closedAt` null only for a close we could not date.
- `busiestDay` — the America/New_York calendar day (`YYYY-MM-DD`) with the most cases **created** this week (a close of an older case is not a new case), ties to the later day; null when nothing was created.

**Neighborhood rings — one copy.** `shared/neighborhoods.ts` carries the 25 GIS rings (`NEIGHBORHOODS`), `hoodOf(lat, lng)` (bbox reject, then a ray cast over the outer rings) and `hoodSlug`. The Worker imports it eagerly; the app (`app/src/lib/neighborhoods.ts`) loads the same module with a dynamic `import('@shared/neighborhoods')`, so the rings stay their own ~8 KB chunk off the main bundle, and classifies the map feed with its bbox-indexed `hoodOfSync` over that table (the app's `neighborhoods.data.ts` copy was deleted 2026-10-26). An edit to the rings is made once. The app keeps a static `NEIGHBORHOOD_NAMES` list so `?n=` parses before the rings load (a static import of the shared module would inline the rings and defeat the `import()`); `app/tests/unit-streetMap.spec.ts` asserts the list equals the shared keys and that `hoodOfSync` / `neighborhoodAt` agree with `hoodOf`.

## GET /api/me
`{ uid, email, emailVerified, displayName, provider, prefs: { emailUpdates, weekDigest }, addresses: [{ id, label, address, lat, lng, digest }], following: [id], cityFollowing: [guid], push: { endpoints: [string] }, createdAt, quota: { dayUsed, dayLimit, weekUsed, weekLimit, dayResetsAt, weekResetsAt, nextAllowedAt } }`. Creates the user doc on first call. `addresses[].digest` (2026-10-28) is always a boolean: whether that address is in the Monday street digest — its own flag, or for an address saved before per-address flags the old account-wide `prefs.streetDigest` (street.ts `addressDigest`; see PUT /api/me/addresses). `prefs` no longer carries `streetDigest`, `streetWatch` or `watchGroups` (a value still stored on an old doc is never returned). `push.endpoints` = the account's web-push subscriptions (below); the app matches its own `PushSubscription.endpoint` against it to show "Notify me on this phone" as on or off. `quota` times are ISO UTC; `nextAllowedAt` is null when a report would be accepted now (the per-IP backstop is not reflected).

## PATCH /api/me
JSON `{ displayName?: string|null, prefs?: { emailUpdates?: boolean, weekDigest?: boolean } }` → the `GET /api/me` shape. `emailUpdates:false` silences city-status mail for own + followed reports. Any other `prefs` key is ignored and nothing is written for it: `streetDigest` (the Monday street digest is per address since 2026-10-28 — PUT /api/me/addresses), and `streetWatch` / `watchGroups` — the street watch (an instant push for a new case near a saved address, with quiet hours and an overnight catch-up in `meta/watchOvernight`) and its "Only tell me about…" group filter, cut 2026-10-28 (worker/src/streetwatch.ts and watchgroups.ts deleted).
`weekDigest:true` opts into the Monday **"This week in Providence"** email (kind `week_digest` in the email log; worker/src/week.ts `runWeekDigest`, from runDaily on Mondays right after the street digest): one mail per opted-in account whose email is verified, the summary of the **Monday–Sunday calendar week that just ended** (`GET /api/week?until=<yesterday NY>`, i.e. the Sunday — not the 168 h ending at the 11:00 UTC cron, whose dated link would mean a different Tue–Mon week from the next day on) — subject `This week in Providence: <total> request(s), <closed> closed`; body: the headline numbers with the vs-last-week delta ("+12 vs last week" / "same as last week"), per reader (2026-10-27) a **"Your neighborhoods"** block right under those numbers — the hoods of the account's saved places (`addresses[]` with coordinates, in saved order, at most the first 5 — the app's `placedAddresses`; each through `shared/neighborhoods hoodOf`, once each, a place outside every ring left out; `week.ts readerHoods`), at most 3, one line each linked to `<APP_BASE_URL>/street?n=<slug>`: `<Hood>: N request(s), M closed · median X day(s)` (the median left out when the hood had no dated close) or `<Hood>: nothing this week`, then for the first of them with a median (when the city has one) `Closed requests in <Hood> took a median X days — the city's was Y.`; read from the user docs the run's `listWeekDigestUsers` query already returns (no read per recipient), and an account with no placed address in a ring gets the shared mail, byte for byte as before; English only, like the rest of this mail (there is no per-account language) — then the top 3 case types with last week's count, the 3 busiest neighborhoods, 3 notable closes with the city's note, "See the whole week" → the **dated** page `<APP_BASE_URL>/week?until=<untilDate>` = that Sunday (so the page reproduces the mailed numbers exactly, next week and next month), "You asked for this every Monday on FixMyPVD. Change or stop these emails under Account → Updates" (→ `<APP_BASE_URL>/account/updates`, the footer every resident mail carries — notify.ts `updatesLine`) and the not-affiliated footer. A week with `total === 0` sends nothing to anyone. The same Monday run also mails Rob **one** admin mail (`mailer.alert`, subject `[FixMyPVD] Your r/providence post for this week`, kind `admin_digest`; 2026-10-26) with the week as the ready-to-paste r/providence Markdown post — byte for byte what `/week`'s "Copy as post" copies (`shared/weekPost.ts weekPostMarkdown`, used by both) in a `white-space:pre-wrap` `<pre>`, a "Copy it from the week page" link to the dated page and the not-affiliated footer — whether or not anyone opted in, never on an empty week; the `week.digest` event, `meta/weekDigest` and the run's return carry `adminMailed`. Both Monday mails also go to subscribed phones as a push (`runWeekDigest` / `runStreetDigest`, below under "Notify me on this phone").

List (same shape as `/api/me/reports`, `mine` false) / follow (204) / unfollow (204). Followers with `emailUpdates` on get the same city-status mail as the reporter (gated like all reporter mail). Use PUT from the "already reported nearby" prompt when signed in, instead of `/follow {email}`.

## GET /api/me/city · PUT /api/me/city/:guid · DELETE /api/me/city/:guid — follow a public city case
Any case on the city's public list (`cityCases/{guid}`, the cards on `/street`), ours or not (worker/src/cityfollow.ts, routes in me.ts). `guid` = the city's case GUID, `/^[0-9a-f-]{36}$/`. PUT → 204 (404 `not_found` when no such case; idempotent). DELETE → 204 (idempotent, also for a case whose record is gone). `users/{uid}.cityFollowing` holds the GUIDs newest first, ≤100 — a full list lets the oldest follow go and that case forgets the account; `cityCases/{guid}.followerUids` ≤200. `users/{uid}.cityFollowedAt` (guid → ISO) remembers when, for `followedAt`.
GET → `{ items: FollowedCase[] }` in `cityFollowing` order (newest follow first): `{ id, caseType, category, street, status, open, createdAt, closedAt, resolution, lat, lng, followedAt, updatedAt }` — `open` = status not in Resolved / Closed / Cancelled / Merged; `closedAt` = the city's resolution date, else the close the sync watched happen (`cityinsights.closedAt`), closed cases only; `resolution` = the city's Resolution Message trimmed, or null; `followedAt` = when this account followed it (null for a follow recorded without it); `updatedAt` = `statusAt`, when the sync last saw the city move it. A case whose record vanished is skipped.
Mail — kind `city_follow` in the email log. When the 30-min sync (worker/src/citycases.ts, list status) or the daily follow-up (detail status, for open cases that left the 7-day window) sees a followed case's status move, each follower with a verified email and `prefs.emailUpdates` on gets ONE email from `mailer.sendTo`: subject `City update: <caseType> on <street> — <status>`; body: what the city did in notify.ts's neutral voice (old → new status), the city's Resolution Message as a blockquote when present, "Reported <date>", "See it on the map" → `<APP_BASE_URL>/street?case=<guid>&lat=&lng=` (lat/lng only when the case is located; the page opens the card from `case=` either way), "You follow this request on FixMyPVD. Change or stop these emails under Account → Updates." (→ `<APP_BASE_URL>/account/updates`) and the not-affiliated footer. Never to the city. Once per status: `cityCases/{guid}.notifiedStatus` = the status last mailed, skipped when it equals the current one. A followed case that moved gets its detail read in the same run, ahead of the per-run detail cap, so a closing mail carries the Resolution Message. Mail failures never break the sync; the health note counts `N follow mails`. A followed open case is not forgotten after 60 days like other open cases: the daily follow-up marks index entries whose doc has followers (`f`, checked from three days before the prune and daily after it, cleared when the last follower leaves), keeps them up to a year, and reads them first in the day's budget — so the closing mail still comes for a sidewalk or tree case that takes months. Followers who subscribed a phone (`POST /api/me/push`, below) also get the same move as a push, right after the mail — see "Notify me on this phone".

## GET /api/push/key · POST /api/me/push · DELETE /api/me/push — "Notify me on this phone" (added 2026-10-26)
Web push alongside email, never instead of it (worker/src/push.ts; pure WebCrypto, no npm dependency). **Having a subscription is the opt-in** — there is no `prefs` key; the app shows unsupported / needs-install (iOS Safari, until added to the Home Screen) / blocked / on / off from the browser state plus `GET /api/me`'s `push.endpoints`.
- `GET /api/push/key` (public, `cache-control: public, max-age=3600`) → `{ publicKey }`: the VAPID public key, base64url of the raw 65-byte P-256 point, for `PushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`. **The key pair is minted by the Worker on the first call** (`ensureVapid`) and kept in Firestore `meta/vapid` — `{ publicKey, privateJwk, createdAt }`, the private key as a JWK — so there is no secret to set with wrangler. It never rotates on its own: deleting `meta/vapid` would invalidate every stored subscription (push services reject a VAPID key that is not the one the subscription was made with).
- `POST /api/me/push` JSON `{ endpoint, keys: { p256dh, auth }, ua? }` (`PushSubscription.toJSON()` plus the user agent, ≤200 chars) → 204. Validated: an `https:` endpoint ≤2048 chars, `p256dh` a 65-byte uncompressed P-256 point, `auth` 16 bytes (base64url or base64, padded or not; stored normalised); else 400 `invalid_subscription`. Upsert by `endpoint` into `users/{uid}.push[]` — `{ endpoint, p256dh, auth, ua, createdAt, lastUsedAt }` — newest first, a re-registration keeps its `createdAt`; **≤5 per account, the oldest dropped**. **One owner per endpoint** (`claimPushEndpoint`): `pushEndpoints/{sha256(endpoint) hex}` = `{ uid, updatedAt }` names the account a browser subscription belongs to; when a POST arrives for an endpoint the index gives to another account (a previous user of a shared or handed-down phone who did not turn push off), that account's `push[]` loses the endpoint first (one read + one patch, best effort) — so a phone only gets the pushes of whoever is signed in on it, and never two accounts' at once. DELETE and the 410 pruning leave the index entry; a stale one costs the next claim a `getUser` that finds nothing to strip. The app also does its part: `signOut()` (lib/auth) sends `DELETE /api/me/push` for this phone's subscription with the bearer that was just valid and then drops the browser subscription, best effort.
- `DELETE /api/me/push` JSON `{ endpoint }` → 204, idempotent (400 `invalid_body` without an endpoint).
- Sending (`sendPush`): one RFC 8291 / RFC 8188 `aes128gcm` message per subscription — fresh ECDH P-256 key and 16-byte salt each time, record size 4096, one record, padding delimiter `0x02`, verified against RFC 8291 Appendix A in `worker/test/push.test.ts` — POSTed to the endpoint with `Authorization: vapid t=<ES256 JWT { aud: the push service origin, exp: +12 h, sub: mailto:rob@fixmypvd.org }>, k=<publicKey>`, `Content-Encoding: aes128gcm`, `Content-Type: application/octet-stream`, `TTL: 86400`, `Urgency: normal`. Payload JSON `{ title, body, url, tag }` — the app's service worker shows it (same `tag` replaces the earlier notification) and opens `url` on tap. **404 / 410 from the push service = the browser dropped the subscription**: `pushAll` removes it from the account (one write, only then; the surviving ones get `lastUsedAt`). Any other failure is logged and counted; it never throws into a sync or a digest.
- Triggers — each one right after the corresponding email, and only there:
  - **your own report's city status moves** (`notifyStatusChanges` in worker/src/engine.ts, after the watcher's 30-min My Requests diff and detail read; added 2026-10-28): right after the status mail (kind `status`), every subscription of the report's owner (`ownerUid` — an anonymous report has none) gets `{ title: <the mail's phrase, e.g. "The city closed your request">, body: "<category> at <address> — <status>" (+ " · " + the first 80 chars of the city's Resolution Message when there is one), url: <APP_BASE_URL>/r/<id>, tag: "report:<id>" }` — **regardless of email settings** (`push.ts pushOwner`); the report's followers get the mail only;
  - **the city asks you a question** (`syncCityAsks`, worker/src/cityask.ts — from relay.ts when the city's mail arrives, or the watcher from a portal note; added 2026-10-28): beside the owner's "The city needs more information" mail — the newest new ask only, while it is answerable and found within 7 days — every subscription of the owner gets `{ title: "The city needs more information", body: "Your <category> report at <address> (<case id>) — answer on your tracking page", url: <APP_BASE_URL>/r/<id>#answer, tag: "ask:<id>" }`, once per ask (the 48 h reminder is mail only; an ask on a closed case or found late gets neither);
  - a followed city case moves (`notifyCityFollowers`): every follower whose list still holds the case and who has subscriptions, **regardless of email settings** (a subscription is its own opt-in; `cityfollow.pushFollowers`) gets `{ title: "City update: <caseType>", body: "<street> — <old> → <new>" (+ " · " + the first 80 chars of the Resolution Message when the new status is a close), url: the same /street?case=… link as the mail, tag: "case:<guid>" }`; once per status, under the same `notifiedStatus` guard as the mail;
  - the Monday week digest (`runWeekDigest`): every account with `prefs.weekDigest` and subscriptions — verified email or not — gets `{ title: "This week in Providence", body: "<total> request(s) · <closed> closed", url: <APP_BASE_URL>/week?until=<untilDate> (the dated page the mail links), tag: "week" }` — plus, when one of the account's "Your neighborhoods" (the mail's ≤ 3) had activity, the first such appended: ` · Fox Point: 30 requests, median 4.5 d` (the median left out without one; otherwise the body is unchanged); a week with no cases pushes nothing;
  - the Monday street digest (`runStreetDigest`): one push **per saved address with activity** — `{ title: "This week near <label>", body: "<new> new · <closed> closed", url: that section's /street?lat=&lng=&q= link, tag: "street:<address id>" }` (tagged per address so two addresses do not overwrite each other); mail still needs a verified email, the push only the subscription; only addresses whose `digest` is on (PUT /api/me/addresses, below);
- Log: kind `push.sent` (level info) per run that reached a subscribed account — `data: { source: report_status | city_ask | city_follow | week_digest | street_digest, users, sent }`; the digests' own `week.digest` / `street.digest` events and `meta/weekDigest` / `meta/streetDigest` records carry `pushed` too. Mails keep their kinds.

## PUT /api/me/addresses · DELETE /api/me/addresses/:id
PUT JSON `{ id?, label?, address (3–300), lat?, lng?, digest? }` (lat/lng both or neither) → `{ addresses }`, each with `digest: boolean` (≤10, 400 `too_many` past that; an `id` already saved = edit that address **in place**, keeping its position; otherwise a new address, first in the list). DELETE → `{ addresses }`.
**The Monday street digest is per address** (2026-10-28): `digest: true` puts that address in the Monday "This week near …" email (kind `street_digest`; worker/src/street.ts `runStreetDigest`, from runDaily on Mondays): one mail per account listing the cases created or closed in the last 7 days within 300 m of each address that is on (an address that is on but has no coordinates is geocoded then; one that is off never is); no activity, no mail. A **new address starts off** (`digest` absent → false — saving a place to report from no longer subscribes it); an edit keeps the address's flag unless the body sets one; anything but `true` is off. Migration: the effective flag is `address.digest ?? (prefs.streetDigest === true)` (street.ts `addressDigest`) — an account from before had one account-wide switch, which covered every address it had. Every PUT and DELETE writes the list with each address's flag explicit (its effective value at that moment, so the old switch is pinned onto the addresses it covered and never leaks onto later ones) plus `prefs.streetDigest` = "at least one address is on" — no longer a setting (PATCH ignores it) but the index `runStreetDigest` reads (`listStreetDigestUsers`, Firestore equality, ≤ 500). Footer: "You asked for this weekly email on FixMyPVD. Change or stop these emails under Account → Updates." (→ `<APP_BASE_URL>/account/updates`).

## Changes to existing endpoints
- `POST /api/report`: account required (above). `GET /api/reports/:id` with a bearer adds `mine`, `following`, `editable`, and `description` (owners only); always adds `owned` and `cancelledByReporter` (status `rejected` + this flag = the reporter withdrew it).
- HITL trust ramp (`HITL_MODE=ramp`, the launch mode): the first `ACCOUNT_TRUST_N` (3) reports of each account are human-reviewed; after that, an account with 0 rejected reports — or `users/{uid}.trusted=true` — auto-approves. `HITL_MODE=review` = every report tapped (panic switch).

## City email relay (ops, not app-facing) — added 2026-09-28
The portal account's contact email is `cases@fixmypvd.org` (Cloudflare Email Routing rule → this Worker's `email()` handler, `worker/src/relay.ts`). A city email carrying a `PVDyyyy-nnnnn` case id we filed is forwarded to that report's reporter + followers from `updates@fixmypvd.org` with `Reply-To: cases@fixmypvd.org`, and appended to `report.cityMessages` (last 20, each tagged `kind` receipt / routed (+`dept`) / ask / update, with its `messageId`; the tracking `timeline` words them by kind). When the city ASKS the reporter for something, the owner gets "The city needs more information about your report" instead of the plain copy (followers still get the copy), the ask is recorded in `report.cityAsks`, and the owner's reply (DMARC pass, from their address) is sent to the city from `cases@fixmypvd.org` — see `POST /api/reports/:id/answer`. That answer is the only thing ever sent to the city automatically. City mail with no matching case, and anything else written to the relay, goes to `NOTIFY_EMAIL`. Auto-replies, bounces and our own domain are dropped. If handling throws, the raw mail is forwarded to `RELAY_FALLBACK_TO`.
- `GET|POST /admin/portal/profile` (x-canary-token) — read the portal profile form, or `{ "email" }` to set the contact address.
- `PORTAL_NOTIFY_METHOD` var — `#cop_methodofupdate` value used on Step 1 (`585680002` Email once the relay is the profile address; default `585680003` No Contact Necessary).

## HITL (ops, not app-facing)
Review emails carry signed links `GET /hitl/approve/:id/:exp/:sig` and `/hitl/reject/:id/:exp/:sig` (HMAC-SHA256 over `action:id:exp`, 30-day expiry; path form so a quoted-printable mis-decode in transit can't corrupt them). Any intake flag — client-reported or from the Worker's own moderation pass, which runs once per report before auto-approval — forces human review regardless of account trust. No Turnstile: the required sign-in is the human check (since 2026-10-17). Pacing is per mailbox (plus-tags and gmail dots collapsed) and per IP.
